# 設計フェーズの学習と反省

## プロジェクト設計で重視した点

### 1. モジュール化と責務分離
自動売買ロジックを 8 つの上位モジュールに分割し、さらに下位部品へ分解することで以下を目指した。
- 各モジュールの責務を明確化する
- 単体テストと結合テストをやりやすくする
- 変更時の影響範囲を局所化する
- 後から裁量知見を追加しやすくする

### 2. 段階的テスト戦略
テストを後回しにせず、下位部品単体 -> 上位モジュール結合 -> モジュール間結合 -> 通し確認の順で考える方針を取った。

### 3. 事前設計の重要性
実装前に以下を明確にすることを重視した。
- モジュール境界
- 主要変数
- 状態遷移
- テスト観点
- agent 運用方法

## 得られた知見

### アーキテクチャ設計
- `HTFContext` と `LTFStructure` を分けることで、方向判断とタイミング判断の責務が明確になった
- `RiskFilter` と `Execution` を分けることで、安全性と実行制御を整理しやすくなった

### テスト計画
- 停止条件と状態遷移は、売買条件そのものと同じくらい重要
- 理由記録を前提にすると、テスト観点も整理しやすい

### ドキュメント運用
- repo 内文書だけで継続できる状態を先に作ると、会話履歴依存を下げやすい
- SoT と外部説明用文書を分けることが重要

## 今後の課題と改善点

### 実装段階での期待される課題
1. 大量データ処理時の速度最適化
2. 市場の異常時やデータ不整合時の安全動作
3. 各判定部品の閾値やルールの調整
4. 診断出力（HTF comparison / lot sizing shadow）の継続運用と説明粒度の標準化

### 設計の見直しポイント
- 実装を進める中で、モジュール間インターフェースの不足や過剰が見える可能性がある
- `docs/10_interface_contract.md` は次フェーズで SoT との再整合が必要
- portfolio 文書は設計確定に追従して定期的に更新する必要がある

## 現時点の位置づけ（重要）
- このプロジェクトは収益性確認済みEAではなく、分析/検証基盤である。
- 実 broker / OANDA API / 実注文送信は未実装である。
- `PositionSizer` は placeholder で、lot sizing 本体接続は未実装である。
- HTF は diagnostic comparison v0 を完了した段階であり、本体filter採用ではない。
- lot sizing は shadow comparison tool（diagnostic用途）として採用している。

## 個人的な学習成果

- 状態管理を含む設計整理

### 次のプロジェクトへの適用

# DECISION LOG

## 1. 目的
本ファイルは、このプロジェクトにおける重要な設計判断と、その理由を記録するためのものである。

## 2. 初期判断

### Decision 001
#### 内容
主対象を USDJPY とする。

#### 理由
現時点での主要な想定対象であり、裁量時の観察と構想の基準になっているため。

#### 補足
ただし構造は USDJPY 固有に閉じず、他商品への流用可能性を意識する。

#### 内容

#### 理由
5分足でタイミングを取りつつ、1時間足・4時間足で方向と余地を確認する裁量思想を反映するため。

#### 理由

### Decision 009
#### 内容
LTFStructure 系の正式理由変数は `pattern_reason` に統一する。

`breakout_reason` は正式契約変数にしない。残す場合は BreakoutDetector 内の内部補助情報に限定し、モジュール境界・SoT・Logger の正式変数には含めない。

また、`breakout_flag = true` のときは、根拠が `pattern_reason` から追跡可能であることを要件とする。

#### 理由
理由変数を一本化し、`docs/05`、`docs/07`、`docs/10` 間の命名ズレを解消して契約とテスト観点を安定化するため。

---

### Decision 010
#### 内容
Data モジュールの検証失敗返却は、失敗結果方式を正式方針とする。

具体的には `data_valid_flag = false` と `validation_reason` を返す。

例外は、入力契約違反または処理継続不能な障害に限定する。
- 必須列不足
- 時刻列解釈不能
- 読み込み元不存在
- タイムフレーム指定不正

単なる市場データ異常の検出や検証NGは、原則として例外ではなく失敗結果で返す。

後続モジュールは `data_valid_flag = false` の場合に進まない。

#### 理由
Data の失敗時挙動を一貫化し、`docs/04`、`docs/07`、`docs/10` の契約とテスト観点のズレをなくすため。

---

### Decision 011
#### 内容
状態遷移情報は `event_logs` に含めず、`state_logs` という専用ログ集合に分離する。

`state_logs` は状態機械の制御履歴を追跡するための正式ログ集合とし、最低限 `docs/06_state_spec.md` 8章の以下を対象とする。
- `position_state`
- `previous_state`
- `next_state`
- `transition_reason`
- `order_result`
- `execution_reason`
- `log_time`

`event_logs` は停止・見送り・イベント関連記録に限定し、`trade_logs` は約定・損益中心、`decision_logs` は判断理由中心とする。

Evaluator は `state_logs` を独立入力として扱う。

#### 理由
状態遷移をイベント記録と混在させず、Logger / Evaluator / 状態仕様（`docs/06`）の責務境界を明確化するため。

---

### Decision 012
#### 内容
Evaluator の初期版指標セットを以下で固定する。

基本成績指標（正式）:
- `trade_count`
- `win_rate`
- `average_pnl`
- `profit_factor`
- `max_drawdown`

分析補助指標（正式）:
- `structure_type_stats`
- `filter_hit_stats`
- `signal_type_stats`

初期版の期間単位:
- 全期間
- 月次
- 構造種別ごとの集計単位

初期版の比較軸:
- `structure_type`
- `signal_type`
- `filter_reason`
- 必要に応じて `event_type`

初期段階では、シャープレシオ等の高度指標、時間帯別・曜日別の詳細分析、補助AI由来の複雑比較指標、多数の派生比率指標は扱わない。

#### 理由
実装前に最小限の評価範囲を固定し、`docs/04`、`docs/05`、`docs/07`、`docs/10` の未確定事項を解消して比較可能性を優先するため。

### Decision 013
#### 内容
Data モジュール実装前のデータ受け入れ基準とデータ役割分担を以下で固定する。

データ形式の役割:
- 年次 CSV（Dukascopy 由来）は一次ソース候補とする
- parquet は正規化済み高速処理用とする
- pkl は作業キャッシュとする
- pkl は正本にしない

採用判定は用途ごとに分ける:
- 構造検証用として採用可能か
- バックテスト基準として採用可能か
- 実運用近似として採用可能か

受け入れ基準には最低限以下を含める:
- spread
- bid/ask
- volume
- timezone
- 欠損
- H1/H4 集約ルール

Dukascopy を無条件で真実と断定せず、上記基準を満たした場合に用途別採用を行う。

詳細は `docs/11_data_source_policy.md` を正とする。

#### 理由
Data モジュールの入力品質と用途別妥当性を実装前に固定し、正本・キャッシュ・採用基準の混在を防ぐため。

---

### Decision 014
#### 内容
初期段階の main に導入する執行足構造パターンは `third_wave_break` のみとする。

`triangle_break` は `experiments` 領域で先行検証し、本体への導入は後段で判断する。

複数パターンが同時に成立しそうな競合ケースは、初期段階では安全側を優先し、見送りとして扱う。
このとき、少なくとも `structure_candidate = false`、`structure_type = none`、`structure_direction = neutral` を基本とし、理由は `pattern_reason` に残す。

#### 理由
初期段階で main に複数パターンを同時導入すると、原因切り分け、挙動確認、テスト整理、採用判断が難しくなるため。
まずは `third_wave_break` 単体で end-to-end の挙動と追跡可能性を安定させ、その後に `triangle_break` を比較可能な形で検証する。

---

### Decision 015
#### 内容
AI 運用の通常主力は 5.3 Codex（VSCode auto）とし、5.4 系は難所限定で使用する。

運用固定:
- 5.4thinking（チャット/アプリ）は最上流判断専用
- 5.4（VSCode）は repo 横断の難所や広域整合でのみ使用
- Copilot / Cursor は仕様確定後の機械実装・骨組み作成に使用
- Human が採用 / 保留 / 却下を決定

コスト最適化:
- 1ファイル修正や単純追記では 5.4 を使わない
- docs 3枚以上に波及する判断や難所だけ 5.4 を使う
- 通常の docs 追記・整合・実装補助は 5.3 Codex を優先する
- 依頼は 1目的・少数ファイルに分割する

#### 理由
役割境界と 5.4 使用条件を固定し、日常運用コストを抑えながら docs / 実装 / テスト整合の速度を維持するため。

---

### Decision 016
#### 内容
資産クラス拡張は、Core Framework を市場非依存に保ち、FX固有仕様は FX Adapter、株式固有仕様は将来の Equity Adapter に分離する方針を採用する。

#### 理由
既存のFX実装・backtest・Data契約を維持しながら、将来の株式拡張で作り直しや仕様混在を防ぐため。

#### 補足
- 現時点では株式対応の実装・検証は行わない。
- 詳細は `docs/18_asset_class_extension_policy.md` を参照する。

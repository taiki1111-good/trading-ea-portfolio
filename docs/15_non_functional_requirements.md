# 非機能要件

## 1. 文書の目的
この文書は、`trading-ea` の設計・実装で重視すべき非機能要件を整理する。
`docs/02_requirements.md` で示された品質要求を具体的な確認観点に落とし込む。

## 2. 説明可能性
### 定義
- 各判断の理由が追跡できること
- `Logger` で `signal_reason` / `filter_reason` / `execution_reason` / `transition_reason` が残ること

### 確認観点
- ログからエントリー／見送り／停止の理由が再現できるか
- `signal_reason` が成立条件を説明しているか
- `transition_reason` が状態遷移の根拠を表しているか
- `execution_reason` が注文結果の背景を示しているか

## 3. 保守性
### 定義
- モジュール・変数・状態が明確に分離され、修正が局所化しやすいこと

### 確認観点
- `docs/04_module_spec.md` の責務分割が実装に反映されているか
- 1部品修正で他部品への影響が最小限にとどまるか
- 変更時に `ops/DECISION_LOG.md` と `ops/review/` の運用が使われるか
- モジュール名や変数名が `docs/05_variable_spec.md` と整合しているか

## 4. 信頼性
### 定義
- 異常やデータ不整合時に安全側に振る舞うこと

### 確認観点
- `DataValidator` が未検証・不正データを検知できるか
- `ERROR` / `SUSPENDED` へ安全に遷移できるか
- 二重エントリーや停止中発注が防止されるか
- リスクフローが `docs/06_state_spec.md` と一致しているか

## 5. テスト容易性
### 定義
- 下位部品単体テスト・上位結合テスト・シナリオテストが実施しやすい構造であること

### 確認観点
- `docs/07_test_plan.md` の層別テスト方針が実装に反映されているか
- 部品に対して契約テストが書けるか
- `tests/unit/` `tests/integration/` `tests/scenario/` が構成されているか
- `experiments` 用のテストも分離されているか

## 6. 拡張性
### 定義
- 新しい裁量パターンや補助判定を既存部品を大きく壊さず追加できること

### 確認観点
- `docs/03_architecture.md` の層別構成が維持されているか
- `LTFStructure` と `Signal` が拡張可能な設計か
- `experiments` 領域のコードと本体が分離されているか
- 既存の責務を保ったまま新規処理を追加できるか

## 7. 移植性
### 定義
- USDJPY を主対象としつつ、他通貨ペアや他商品への流用可能性を残すこと

### 確認観点
- データ依存が USDJPY 固有になっていないか
- モジュールが時間足や商品の切り替えに耐えられるか
- `docs/02_requirements.md` の「商品依存分離」方針が維持されているか

## 8. 安全性
### 定義
- 誤発注・誤決済・異常継続を防止すること

### 確認観点
- `RiskFilter` が `spread` / `event_flag` / `trade_limit` をチェックするか
- `position_state` が適切に管理されているか
- `ERROR` / `SUSPENDED` が危険動作を停止するか
- 実行フローに安全境界があるか

## 9. 運用性
### 定義
- 実装後の運用・監視が現実的であり、次工程へ移行しやすいこと

### 確認観点
- ログの粒度が運用に耐えうるか
- 障害時の復旧手順が整理されているか
- `ops/CURRENT_TASKS.md` が次の作業を明確に示すか
- 実験採用・運用停止の境界が明確か

## 10. 再現性
### 定義
- 同じ入力で同じ結果が再現できること

### 確認観点
- 同一データセットで再現テストが可能か
- determinism を担保する構造になっているか
- `docs/11_data_source_policy.md` に沿ったデータ取り込みルールがあるか
- ログに再現に必要な情報が残るか

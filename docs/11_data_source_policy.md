# データソース方針

## 1. 目的
本ドキュメントは、Data モジュール実装前にデータ受け入れ基準とデータ役割分担を固定するための初期版方針である。

対象は主に Dukascopy 由来データ（CSV / parquet / pkl）とする。

## 2. 形式ごとの役割
### 2.1 年次 CSV
- 位置づけ: 一次ソース候補
- 用途: 元データ保全、再取り込み、正規化元
- 注意: 無条件に真実と断定しない。受け入れ基準を満たした場合のみ採用する

### 2.2 parquet
- 位置づけ: 正規化済み高速処理用
- 用途: Data モジュールの実行入力、テスト反復、集計高速化
- 条件: CSV から変換した後に、時刻・列・欠損・値域の検証を通過していること

### 2.3 pkl
- 位置づけ: 作業キャッシュ
- 用途: 一時的な作業短縮
- 条件: 正本にしない。再現可能性の根拠は CSV / parquet に置く

## 3. 受け入れ基準（共通）
以下を最低限の受け入れ判定項目とする。

- `timezone` が明示され、単一基準へ統一できること（初期版は UTC 基準）
- `timestamp` が解釈可能で、重複・逆順が許容範囲内であること
- OHLC の欠損・破損・異常値が判定可能であること
- `spread` の有無、単位、意味が判定できること
- `bid` / `ask` の有無と意味が判定できること
- `volume` の有無と意味（tick/real）が判定できること
- 欠損バー・欠損期間を検出できること
- H1/H4 集約ルールが固定され、未来参照なしで再現できること

補足:
- 共通基準では「存在必須」ではなく「有無と意味を判定できること」を求める
- 実際の必須性は用途別採用判定（構造検証用 / バックテスト基準 / 実運用近似）で確定する

### 3.1 時刻・セッション・日付境界の初期方針
- Data の正規化後時刻基準は UTC とする
- 日付境界は `00:00 UTC` とする
- H1 バケット開始時刻は各時 `HH:00 UTC` とする
- H4 バケット開始時刻は `00:00 / 04:00 / 08:00 / 12:00 / 16:00 / 20:00 UTC` とする
- 初期版では DST 依存の境界を使わず、UTC 境界を正式基準とする

### 3.2 欠損時の代替・近似ルール
#### spread 欠損時
- `spread` は最終的に pips 単位へ正規化する
- 一部行のみ欠損している場合は、同一ファイル内の直前有効値で forward fill する
- ファイル先頭欠損または列全体欠損の場合、USDJPY の初期固定 fallback として `0.2 pips` を使う
- 固定 fallback `0.2 pips` の利用は構造検証用とバックテスト基準まで許容し、実運用近似では許容しない

#### bid / ask 欠損時
- `bid` / `ask` が欠損し、`spread` が利用可能な場合は close を mid とみなし再構成する
- USDJPY の初期 pip size は `0.01` とする
- 再構成式は以下とする
  - `bid = close - (spread_pips * 0.01 / 2)`
  - `ask = close + (spread_pips * 0.01 / 2)`
- 再構成 `bid` / `ask` はバックテスト基準まで許容し、実運用近似では actual bid/ask と同等扱いしない

#### volume 欠損時
- 欠損または空値の `volume` は `0` に正規化する
- 現行 main では volume を売買条件に使わないため、`volume = 0` だけでは採用不可にしない
- ただし、tick volume と real volume の意味が混在し、識別不能な場合は採用不可とする

### 3.3 H1 / H4 集約ルール
- 集約元は UTC 基準で整列済みの M5 バーとする
- バケットは左閉右開区間 `[start, end)` とする
- 集約時の各値は以下で固定する
  - `open`: バケット先頭バーの `open`
  - `high`: バケット内 `high` の最大値
  - `low`: バケット内 `low` の最小値
  - `close`: バケット末尾バーの `close`
  - `volume`: バケット内 `volume` の総和
  - `spread`: バケット末尾で有効な `spread`
- バケット末尾で `spread` が欠損している場合は、3.2 の spread ルールを適用する
- 不完全な末尾バケットは H1/H4 の正式出力に含めない
- LTF から参照する HTF バーは、`ltf_timestamp` 時点で確定済みのバケットに限る

## 4. 用途別の採用判定
### 4.1 構造検証用として採用可能
最低条件:
- `timestamp` と OHLC が連続的に扱える
- timezone が統一されている
- H1/H4 集約ルールが再現可能

補足:
- `spread` / `bid` / `ask` は欠けても構造検証自体は可能な場合がある
- ただし欠落状況は明示的に記録する
- `spread` 欠損時は `0.2 pips` fallback を許容する
- `bid` / `ask` 欠損時の再構成は任意であり、構造検証自体の必須条件ではない
- `volume` は `0` 正規化を許容する

### 4.2 バックテスト基準として採用可能
最低条件:
- 構造検証用条件を満たす
- `spread` が利用可能、または代替ルールが固定されている
- 欠損と外れ値の扱いがルール化されている
- `volume` の有無と利用方針が固定されている

補足:
- `spread` は actual 値、forward fill、または `0.2 pips` fallback のいずれかで埋められていること
- `bid` / `ask` は actual 値が望ましいが、3.2 の再構成を許容する
- `volume = 0` 正規化を許容する
- `pkl` 単独ではバックテスト基準の正本にしない

### 4.3 実運用近似として採用可能
最低条件:
- バックテスト基準条件を満たす
- `bid` / `ask` が利用可能、または近似ルールが固定されている
- 実運用を想定した時間基準（セッション・日付境界）と整合している
- `spread` の変動を反映できる

補足:
- 実運用近似では `spread` の fixed fallback `0.2 pips` を許容しない
- `bid` / `ask` 再構成は、actual spread がある場合に限り許容する
- 日付境界は `00:00 UTC` と一致していることを要件とする

### 4.4 採用不可条件
以下のいずれかに該当する場合は採用不可とする。

- timezone が混在し、UTC へ一意に統一できない
- `timestamp` が解釈不能、または逆順・重複を解消できない
- OHLC が破損しており、`high >= max(open, close)`、`low <= min(open, close)`、`high >= low` を満たさない
- H1/H4 集約が 3.3 のルールで再現できない
- `spread` 欠損に対して 3.2 のルールを適用しても埋められない
- 実運用近似で、actual spread も actual bid/ask もなく、bid/ask 再構成もできない
- `volume` の意味が行単位で混在し、tick / real を識別できない
- `pkl` しか存在せず、CSV または parquet に再現根拠を戻せない

## 5. Data モジュールでの扱い
- 受け入れ判定は Data で実施する
- 検証NGは `data_valid_flag = false` と `validation_reason` で返す
- 入力契約違反・継続不能障害は例外とする（`docs/04_module_spec.md` の DataValidator 方針に従う）
- 初期版の正規化順は以下とする
  1. timestamp を UTC へ統一する
  2. OHLC / spread / volume / bid / ask を正規化する
  3. 欠損時は 3.2 のルールを適用する
  4. H1/H4 を 3.3 のルールで集約する
  5. 用途別採用判定を 4章で行う

## 6. テストとの接続
`docs/07_test_plan.md` で以下を確認対象とする。
- 形式ごとの役割違反がないか（pkl を正本扱いしない）
- 共通受け入れ基準（spread / bid-ask / volume / timezone / 欠損 / H1/H4集約）の判定ができるか
- 用途別判定（構造検証用 / バックテスト基準 / 実運用近似）が区別されるか

# アーキテクチャ

## 1. 全体方針
本システムは、裁量的に行っていた判断を、そのまま一つの売買条件に押し込むのではなく、複数の責務に分解したモジュール群として構成する。

特に、
- 上位足の環境認識
- 執行足の構造認識
- シグナル統合
- リスク・イベントフィルター
- 注文実行と状態管理

を分離することを基本方針とする。

また、本システムは、採用済みロジックとは別に、新規裁量パターンを試作・比較するための実験領域を持つことを想定する。

## 2. 全体構成
本システムは、以下の流れを基本構成とする。

Data → HTFContext → LTFStructure → Signal → RiskFilter → Execution → Logger → Evaluator

## 2.1 階層構造
本システムでは、上位モジュールをそのまま巨大な処理単位として実装するのではなく、それぞれを複数の下位モジュールで構成することを前提とする。

例:
- HTFContext = TrendDetector + ResistanceDetector + SupportDetector + ContextAssembler
- LTFStructure = SwingExtractor + WaveClassifier + TriangleDetector + BreakoutDetector + StructureAssembler
- RiskFilter = EventFilter + SpreadFilter + TradeLimitFilter + StopLossPlanner + TakeProfitPlanner + PositionSizer + RiskAssembler

この階層構造により、可読性・修正容易性・部品交換容易性を高める。

### 下位部品への分解
上位モジュールは、責務ごとにさらに下位部品へ分解する。
これにより、判定ロジック、フィルター、組み立て処理を分離し、個別に修正・比較・交換しやすくする。

### ボトムアップな組み立て
下位部品を単体で確認し、それらを組み上げて上位モジュールを構成する形を基本とする。
これにより、単体テスト・結合テスト・差し替え実験を行いやすくする。

## 3. 各上位モジュールの位置づけ

### Data
複数時間足の価格データや指標時刻データを読み込み、後続モジュールで扱える形に整える。

### HTFContext
1時間足・4時間足などの上位足を用いて、トレンド方向、抵抗・支持、余地、上位環境を判定する。

### LTFStructure
5分足などの執行足を用いて、第三波候補、高値安値突破などの構造認識を行う。
初期 main では `third_wave_break` を対象とし、`triangle_break` は `experiments` で先行検証する。

### Signal
上位足環境と執行足構造を統合し、エントリー候補・イグジット候補を判定する。

### RiskFilter
シグナルを受けて、取引可否、ロット、損切り、利確、指標前後停止、回数制限などを決定する。
将来的に、EventFilter は外部公式発表や経済カレンダー、速報ニュース入力を受けて危険局面の補助判定や停止閾値補正を行う余地を残す。これらは売買方向決定ではなく、リスク重視の危険検知として扱う。

### Execution
注文実行、約定管理、状態更新を担当する。

### Logger
各モジュールの判断理由、状態、注文結果、損益などを記録する。

### Evaluator
ログや損益情報をもとに、成績評価や改善対象の整理を行う。

## 4. 処理の基本的な流れ
1. Data が価格データと指標時刻データを読み込み、整形する
2. HTFContext が上位足のトレンド方向や抵抗余地を判定する
3. LTFStructure が執行足で波動・ブレイク・持ち合い離脱などの構造を判定する
4. Signal が上位足環境と執行足構造を統合し、売買候補を生成する
5. RiskFilter がイベント、spread、回数制限、損切り、利確、ロットを決定する
6. Execution が注文・約定・状態遷移を管理する
7. Logger が判断理由と結果を記録する
8. Evaluator が成績と改善点を整理する

## 5. 層の考え方

本構成は、初期段階で想定している売買パターンだけでなく、今後新たに見つかる裁量知見も段階的に取り込みやすいように設計する。

### 上位足環境層
ここでは、方向性と余地を扱う。
例:
- 1時間足のトレンド方向
- 4時間足の抵抗・支持
- 上位足の環境バイアス

### 執行足構造層
ここでは、タイミングと形を扱う。
例:
- 第三波候補
- 直近高値・安値突破
- ブレイク強度

補足:
- 初期 main の対象は `third_wave_break`
- `triangle_break` は `experiments` 領域で比較・検証する

### フィルター層
ここでは、「候補があっても入らない理由」を扱う。
例:
- 指標前後
- spread異常
- 当日回数超過
- 連敗停止
- 上位抵抗が近い
- 公式発表・経済カレンダー・速報ニュースなどの外部イベントによる危険検知や停止閾値補正

### 実行・記録・評価層
ここでは、実際の執行と、その後の追跡可能性を担保する。

## 6. 設計上の原則

### 責務分離
上位足判定、執行足構造判定、リスク制御、実行管理を混在させない。

### 単方向データフロー
原則として、上流から下流へ一方向に情報が流れる構造とする。

### 状態の明示
ポジション未保有、注文待ち、保有中、停止中などの状態を明示的に扱う。

### 条件の層別
条件は以下のように分けて扱う。
- コア条件
- 品質向上条件
- 停止条件

これにより、条件追加による取引回数減少の影響を分析しやすくする。

### 説明可能性
エントリー、見送り、停止の理由を記録し、後から追跡できる構造にする。

### 拡張余地
将来的に、相場分類や補助AIを差し込める構造を残す。
また、将来的な資産クラス拡張（FX固有要素の分離と株式向け要素の追加方針）は `docs/18_asset_class_extension_policy.md` を参照する。
本書の責務分離と単方向フローを維持したまま、詳細方針は `docs/18` で future extension として管理する。

### 判断ロジックの追加容易性
新たな裁量パターンや構造認識を、既存のロジック全体を書き換えずに追加・比較できる構造を目指す。

そのため、上位足環境認識、執行足構造認識、フィルター、シグナル統合を分離し、特定の判断要素を差し替えたり追加したりしやすい構造とする。

### 初期 main / experiments 境界
初期段階では、main に複数の構造パターンを同時導入しない。

- main: `third_wave_break`
- experiments: `triangle_break` などの追加候補

複数パターンが同時に成立しそうな競合ケースは、安全側の見送りを優先する。

### 下位部品への分解
上位モジュールは、責務ごとにさらに下位部品へ分解する。
これにより、判定ロジック、フィルター、組み立て処理を分離し、個別に修正・比較・交換しやすくする。

### ボトムアップな組み立て
下位部品を単体で確認し、それらを組み上げて上位モジュールを構成する形を基本とする。
これにより、単体テスト・結合テスト・差し替え実験を行いやすくする。

### docs を基盤とした継続可能性
本アーキテクチャは、特定の会話履歴に依存せず、repo 内の docs 群を参照することで別チャット・別 agent・将来の自分でも継続できることを前提とする。
そのため、重要な責務分離、入出力、状態、運用方針は文書として repo 内に保持する。

## 7. 初期想定の具体的な判断構造
初期 main の構想では、以下のような構造を想定する。

例:
- 1時間足が上昇トレンド
- 5分足で第三波候補が直近高値を突破
- 4時間足に近い抵抗がない
- 指標時刻が近くない
- spreadが許容範囲内

このような条件が揃ったとき、買いの候補とする。

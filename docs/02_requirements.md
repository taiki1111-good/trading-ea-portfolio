# 要件定義

## 1. 目的
本EAは、裁量的に行っていた相場判断を、できるだけ説明可能な形で構造化し、モジュール分割された自動売買システムとして設計・実装することを目的とする。

本プロジェクトでは、短期的な損益だけでなく、以下も重視する。
- 説明可能性
- 保守性
- テストしやすさ
- 拡張しやすさ
- ポートフォリオとして整理しやすいこと

### 1.1 本書の位置づけ
本書は要件定義を扱い、詳細な KPI は `docs/12_project_kpi.md` に、非機能要件の詳細は `docs/15_non_functional_requirements.md` に、運用設計の詳細は `docs/16_operation_design.md` に委譲する。
要件と設計の対応関係は `docs/14_traceability_matrix.md` を参照する。

## 2. 対象市場・対象商品
### 主対象
主対象は FX の USDJPY（ドル円）とする。

### 設計方針
ただし、設計そのものは USDJPY 固有に閉じず、他の通貨ペアや将来的な他商品にも流用可能な構造を意識する。

そのため、
- モジュール責務を分離する
- 特徴量や閾値の差し替えをしやすくする
- できるだけ商品依存の前提を分離する

ことを方針とする。

## 3. 対象時間足
### 執行足
執行の中心は 5分足を想定する。

### 上位足
環境認識のために、1時間足および4時間足を参照する。

### 時間足の役割
- 5分足: エントリータイミングの判定
- 1時間足: 主要トレンド方向や相場環境の確認
- 4時間足: 上位の抵抗・支持や大局的な余地の確認

## 4. 売買思想
本EAの中核は、裁量時に重視していた「構造」を機械的に扱える形に落とし込むことにある。

現時点での中心的な発想は以下である。
- 第三波の進行中における直近高値・安値突破
- 上位足トレンドとの方向一致
- 上位足における抵抗・支持の有無確認
- 確度の高い局面に絞ったエントリー

初期段階の main では `third_wave_break` を優先対象とする。
`triangle_break` は `experiments` 領域で先行検証し、本体への導入は後段で判断する。

### 裁量知見の追加可能性
本EAでは、初期段階の main では第三波の高値・安値突破を中心に扱う。
一方で、三角持ち合い離脱などの追加候補は `experiments` 領域で先行検証し、それに固定することは目的ではない。

開発を進める中で、新たに有効と思われる裁量的な構造や判断要素が見つかった場合、それらを既存システム全体を大きく壊さずに追加・検証できる構造を目指す。

そのため、本システムは、売買判断ロジックを単一の巨大な条件式として固定するのではなく、拡張・差し替え・比較がしやすい形で設計することを要求する。

### 基本姿勢
本システムは、取引回数の多さよりも、条件の整った局面でのみエントリーすることを優先する。

また、複数パターンが同時に成立しそうな場合は、初期段階では安全側を優先し、見送り可能であることを要求する。

ただし、条件を増やしすぎると取引回数が極端に減少し、検証や改善が困難になる可能性があるため、条件は以下のように層別して扱うことを想定する。
- コア条件
- 品質向上条件
- 停止条件

## 5. システムの位置づけ
本システムは、売買判断・リスク管理・状態管理・記録・評価までを含む、ルールベース中核のEAとして設計する。

単なる売買条件の自動化ではなく、以下を含むシステムとして扱う。
- マルチタイムフレーム環境認識
- 執行足構造認識
- エントリー候補判定
- リスク管理
- イベントフィルター
- 注文実行と状態管理
- ログ記録
- 検証・評価
- 外部APIや公式発表は、当面は売買方向の決定ではなく、危険局面の補助判定・停止閾値補正・イベント検知に限定する方針とする。

## 6. システム境界
### 含めるもの
- 価格データを読み込む機能
- 複数時間足を扱う機能
- 上位足トレンド方向の判定
- 上位足の抵抗・支持余地の確認
- 執行足における構造認識
- 売買候補の判定
- ロット、損切り、利確、取引可否の決定
- 注文実行、約定管理、状態管理
- ログ記録
- 成績評価
- 指標発表時刻などを記録したCSV等の読み込み
- 指標前後の取引停止フィルター
- 公式発表、経済カレンダー、速報ニュースを使ったイベント検知や危険局面判定の比較検証基盤

### 含めないもの、または後回しにするもの
- NLPによるニュース本文解析
- リアルタイムのニュースセンチメント分析
- ディープラーニングを中核判断に直結させること
- 本格的な本番運用インフラの作り込み
- 複雑なUI
- 外部APIによる売買方向決定は当面避け、危険局面判定・停止閾値補正・イベント検知への活用に限定する

## 7. 機械学習の位置づけ
### 基本方針
売買判断の中核は、当面はルールベースとする。
理由は、説明可能性と保守性を重視するためである。

### 将来的な利用余地
一方で、機械学習を完全に排除するのではなく、以下の用途では導入余地を残す。
- 相場環境の分類
- レジーム判定
- 危険局面の補助判定
- 曖昧な局面の補助的な整理

### 当面避けること
- ブラックボックス性の高いモデルを、即座に売買中核へ組み込むこと
- ディープラーニングを説明不能なまま本番の中心判断に使うこと
- リアルタイムニュースセンチメント分析は後回しとし、公式発表・経済カレンダー・速報ニュースを使ったイベント検知・停止閾値補正を将来の検証対象とする

### 設計上の要求
将来的に補助モデルを差し込めるよう、モジュール構造は拡張可能にしておく。

## 8. 重視する品質特性
### 説明可能性
なぜそのエントリー・見送り・停止判断になったかを後から追跡できること。

### 保守性
後から条件やモジュールを修正しやすいこと。

### 信頼性
異常状態やデータ不整合時に危険な動作をしにくいこと。

### テスト容易性
各モジュールを単体で確認しやすく、隣接モジュールとの接続も確認しやすいこと。

### 拡張性
将来的に新しい裁量パターン、相場分類ロジック、補助モジュールを追加しやすいこと。
特に、既存の判断ロジック全体を書き換えなくても、新たな構造認識やフィルターを段階的に導入・比較できることを重視する。
特に、新たな裁量パターンや判定部品を、既存部品を大きく壊さず追加・差し替えできることを重要な要件とする。

### 移植性
USDJPY を起点にしつつ、他の通貨ペアや他商品へも流用可能な構造を意識すること。

### 可読性
各モジュールおよび下位部品の責務が明確であり、後から読んだときに意図と役割を把握しやすいことを重視する。

### 修正容易性
特定の判定ロジックやフィルターを修正する際、他の部品への影響をできるだけ限定できることを重視する。

### 高凝集・低結合
各部品はできるだけ単一責務に近づけ、他部品の内部実装に強く依存しない構造を目指す。

特に、新たな裁量パターンや判定部品を、既存部品を大きく壊さず追加・差し替えできることを重要な要件とする。
> 非機能要件の詳細な確認観点は、`docs/15_non_functional_requirements.md` を参照する。
## 9. 基本方針
- モジュールを責務ごとに分離する
- 上位足環境認識と執行足構造認識を分ける
- 上流から順に実装する
- 各段階でテストを挟む
- main は安定版として扱う
- 大きな変更は branch を分けて行う
- 実装と並行して説明資料も整備する

本プロジェクトでは、特定の会話履歴への依存を下げ、repo 内の docs 群を主たる知識源・引き継ぎ基盤として整備することを方針とする。
そのため、重要な設計判断や運用ルールは、可能な限り docs および ops 配下の文書に明示する。

## 10. 評価方針
本システムの評価では、単なる損益だけでなく、以下も確認対象とする。
- モジュール分割が適切か
- 上位足と下位足の責務分離が明確か
- 状態管理が明確か
- 条件の層別ができているか
- テスト方針が整理されているか
- ログから挙動を追跡できるか
- 条件を厳しくしすぎた際に取引回数がどの程度減るかを確認できるか
- 後から改善しやすい構造になっているか

## 11. 制約
- 個人開発で進める
- 設計を先に固めてから実装に入る
- 実装だけでなくポートフォリオ化も行う
- 初期段階では複雑すぎる機械学習依存を避ける
- 最初から完成形を目指すのではなく、段階的に構造化する

## 12. 要件一覧（優先度付き）

本節では、機能要件（FR）および非機能要件（NFR）を、初期段階における優先度付きで整理する。  
優先度は以下の3区分とする。

- Must: 初期版に必須
- Should: 初期版で可能なら含めたい
- Could: 将来拡張として扱う
